This document records the complete step-by-step collaboration behind the **Grand Aurora Hotel · Local RAG Demonstrator**—from the initial `/grill-me` prompt and environment inspection through every architectural decision, implementation milestone, and live verification test.

---

The session began with a `/grill-me` request to interactively resolve all design decisions before writing code:

> **User Request:**
> *"I want to create a local demonstrator for RAG architecture. I would like to deploy locally a small open-weights model like Gemma 4 using Ollama (let's assume I only have 4GB of VRAM on the local GPU). I would like to use EmbeddingGemma 2 for embeddings. For vector DB and vector search I would like to use Chroma DB. Orchestration and the UI should be a locally deployed node website. After submitting the prompt, on the left hand side the user should see a direct reply from the model, while on the right hand side there should be reply from the model with RAG enabled. ## Step 3 · The `/grill-me` Design Interview

Eight focused questions were walked through one at a time, each presenting a recommended option alongside concrete alternatives.

### Question 1 — LLM Configuration & 4 GB VRAM Target
- **Question:** Given `gemma4:e2b` (which defaults to `thinking: true`) and `embeddinggemma-2:270m` are already pulled locally, how should we configure the LLM for the 4 GB VRAM target?
- **Options Considered:**
  1. *(Recommended)* Use `gemma4:e2b` + `embeddinggemma-2:270m` with thinking disabled by default for fast responses, configurable via `.env`.
  2. Use `gemma4:e2b` + `embeddinggemma-2:270m` with thinking enabled (collapsible in the UI).
  3. Enforce a strict `<4 GB` disk footprint using a smaller model (`gemma3:1b` or `llama3.2:3b`).
- **Decision Chosen:** **Option 1** — `gemma4:e2b` + `embeddinggemma-2:270m`, `OLLAMA_THINK=false` and `OLLAMA_NUM_CTX=4096` by default, configurable via `.env`.

### Question 2 — Infrastructure & Chroma DB Deployment
- **Question:** How should we run Chroma DB and the Node.js application?
- **Options Considered:**
  1. *(Recommended)* Docker Compose for Chroma DB + local Node.js server talking to host Ollama.
  2. Everything in Docker Compose (Chroma DB + Node.js containers) talking to host Ollama.
  3. No Docker — run Chroma DB locally via Python (`venv`/`uv`) alongside the local Node.js server and host Ollama.
- **Decision Chosen:** **Option 3 (User Override)** — **No Docker**. Run Chroma DB locally via an isolated Python virtual environment (`chroma-env/`) alongside the local Node.js server and host Ollama.

### Question 3 — Node.js Web Stack
- **Question:** Which Node.js web stack do you prefer for the orchestration server and UI?
- **Options Considered:**
  1. *(Recommended)* Express backend + Vite + React (TypeScript) frontend.
  2. Express backend + plain HTML/CSS/JS frontend (zero build step).
  3. Next.js (TypeScript) full-stack app.
- **Decision Chosen:** **Option 1** — Express + TypeScript backend (`server/`) and Vite + React + TypeScript frontend (`client/`).

### Question 4 — Hotel Rules Knowledge Base (Generation, Storage & Editing)
- **Question:** How should the hotel rules knowledge base be structured, generated, and edited?
- **Options Considered:**
  1. *(Recommended)* Structured rule cards (15–20 categorized hotel rules auto-seeded into local storage + Chroma DB on first run), with Add/Edit/Delete, instant re-embedding on save, Reset to Defaults, and an optional *"Generate Rule with Gemma"* button.
  2. Fully LLM-generated rules on first startup using Gemma 4 (with a *"Regenerate All"* button).
  3. Single editable Markdown hotel handbook split into chunks by section/paragraph.
- **Decision Chosen:** **Option 1** — 18 structured, categorized rules for the fictional *Grand Aurora Hotel* persisted in `data/rules.json`, auto-indexed into Chroma DB, full CRUD with instant re-embedding, Reset to Defaults, and on-demand rule generation via Gemma 4.

### Question 5 — RAG Transparency & Educational Internals
- **Question:** Since this is a RAG demonstrator, how much of the RAG internals should be visible in the UI alongside the answers?
- **Options Considered:**
  1. *(Recommended)* Retrieved hotel rules with similarity scores, an expandable *"Inspect Augmented Prompt"* panel, and latency/token stats on both sides.
  2. Retrieved hotel rules with similarity scores only.
  3. Minimal side-by-side text answers only.
- **Decision Chosen:** **Option 1** — Full transparency: similarity bars & cosine match percentages, retrieval timing, expandable prompt inspector (`<details>`), and `Total` / `TTFT` / token count / `tok/s` stats on both cards.

### Question 6 — Q&A Interaction & Retrieval Tuning Controls
- **Question:** How should the user interact with the Q&A view and tune retrieval?
- **Options Considered:**
  1. *(Recommended)* Single-turn Q&A with clickable sample hotel questions, a shared hotel-concierge system prompt on both sides, and configurable Top-K / similarity threshold controls.
  2. Multi-turn chat conversation history on both sides.
  3. Minimal single-turn Q&A with fixed hardcoded Top-K (`3`).
- **Decision Chosen:** **Option 1** — Single-turn Q&A with 6 clickable sample hotel questions, a shared concierge persona on both sides for a fair comparison, and interactive Top-K (`1–6`) and Min Similarity (`0%–75%`) sliders.

### Question 7 — Streaming & Inference Concurrency (4 GB VRAM Behavior)
- **Question:** How should the two model calls execute and render, given the 4 GB VRAM target?
- **Options Considered:**
  1. *(Recommended)* Live token streaming (SSE), running sequentially by default (Direct first, then RAG) to respect a 4 GB VRAM single-slot budget, with an optional toggle for parallel execution.
  2. Live token streaming (SSE), running both Direct and RAG requests in parallel by default.
  3. Non-streaming (wait for both replies to finish, then display together).
- **Decision Chosen:** **Option 1** — Live SSE streaming, sequential by default for 4 GB VRAM safety, plus a **Run in parallel** checkbox toggle.

### Question 8 — UI Navigation Layout for Hotel Rules Editor
- **Question:** How should the Hotel Rules editor be accessible from the Q&A comparison screen?
- **Options Considered:**
  1. *(Recommended)* Main Split Comparison view with a slide-over Hotel Rules drawer.
  2. Two separate top-level tabs: *"Ask Concierge (Comparison)"* and *"Hotel Rules Manager"*.
  3. Single dashboard page showing the Split Comparison on top and the editable Hotel Rules grid directly below.
- **Decision Chosen:** **Option 2 (User Override)** — **Two separate top-level tabs** (*Ask Concierge (Comparison)* and *Hotel Rules Manager*). To keep live demos effortless across tabs, the last question and results stay preserved in state and a **"Re-run Question"** banner appears on the comparison tab whenever rules are modified.

## Step 4 · Summary Sign-Off & Implementation

After reviewing the consolidated specification, the user gave the green light:

> **User:** *"Go ahead and build it"*

### Key Build Actions
1. **Verified live Ollama APIs:** Confirmed `POST /api/embed` with `embeddinggemma-2:270m` returns 768-dim embeddings (~363–380 MB VRAM) and `POST /api/chat` with `gemma4:e2b` + `think: false` streams cleanly.
2. **Consulted Modern Web Guidance:** Retrieved and applied standards for native `<dialog>` modals (`showModal()`, `overscroll-behavior: contain`, `closedby` fallback), native `<details>`/`<summary>` animated prompt disclosure, `color-scheme: light dark` with `light-dark()` + `prefers-color-scheme` fallbacks, `accent-color` form controls with `@supports not` fallbacks, and `:user-invalid` post-interaction form validation with synced `aria-invalid` / `aria-describedby`.
3. **Provisioned Local Chroma DB:** Created `chroma-env/` using `uv venv --python 3.12` (ensuring prebuilt wheels rather than compiling against Python 3.14) and installed `chromadb==1.5.9` (`chroma 1.4.4`), wrapped in `scripts/setup-chroma.sh` and `scripts/start-chroma.sh`.
4. **Built Backend (`server/`):** Implemented `config.ts`, `types.ts`, `defaultRules.ts` (18 *Grand Aurora Hotel* rules + 6 sample prompts), `ollama.ts`, `chroma.ts` (using `chromadb` JS SDK v3 with `embeddingFunction: null` and cosine HNSW space), `ruleStore.ts` (JSON persistence + Chroma sync), and Express routes (`health.ts`, `rules.ts`, `query.ts`).
5. **Built Frontend (`client/`):** Implemented `App.tsx`, `api.ts` (REST + SSE stream parser), `Header.tsx`, `AskConcierge.tsx`, `ResponseCard.tsx`, `RulesManager.tsx`, `RuleModal.tsx`, and `styles/global.css`.
6. **Build & Fix:** Verified `npm run build` compiled both `server` and `client` with zero TypeScript errors, and tightened `.user-invalid-fallback` reset logic in `RuleModal.tsx` during code review.

## Step 5 · Live End-to-End Verification

The full stack (local Chroma DB + Express server + local Ollama) was booted and verified with live API calls:

1. **Health Check (`GET /api/health`):** Returned `status: "ok"`, Ollama connected with `gemma4:e2b` and `embeddinggemma-2:270m`, Chroma DB connected with `18` indexed vectors.
2. **Side-by-Side Query (`"What time is breakfast served, and which floor is it on?"`):**
   - **Direct Model (No RAG):** Hallucinated *"Breakfast is served daily from 7:00 AM to 10:00 AM on the main dining floor. Please feel free to visit the Grand Ballroom for your morning meal."* (`152.1 tok/s`).
   - **RAG-Enabled Model:** Retrieved *Breakfast Hours & Location* (`85.9%` cosine similarity) and answered *"Breakfast is served daily between 6:30 AM and 10:30 AM in the Wintergarden Lounge on the 2nd floor. This service includes both continental and hot buffet options for all registered guests."* (`355 ms` total, `75 ms` TTFT, `163.6 tok/s`).
3. **Live Rule Edit + Instant Re-Embedding:** Updated `rule-breakfast-hours` via `PUT /api/rules/rule-breakfast-hours` to *"7:15 AM and 11:00 AM in the Sky Atrium on the 9th floor"*; re-running the query immediately produced the updated RAG response.
4. **AI Rule Generation (`POST /api/rules/generate`):** Asked Gemma 4 for a rule about `"bicycle rentals"`; it generated and indexed *"Bicycle Rental Policy"* under `Parking & Transport`.
5. **Clean Reset (`POST /api/rules/reset`):** Restored the 18 default rules and rebuilt the Chroma DB vector collection cleanly.
